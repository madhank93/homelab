# Cloud

> The Pulumi stacks in core/cloud — the Bifrost VPS, Authentik SSO, NetBird mesh and Cloudflare DNS.

# Authentik

> SSO on Bifrost — GitHub login, OIDC for the cluster admin UIs and NetBird, and ForwardAuth for public cluster routes.

Authentik on Bifrost is the single sign-on for everything public: users log in with GitHub, Grafana and NetBird use it over OIDC, and Traefik gates other public routes with ForwardAuth. Fix the cause and re-run `just core hetzner up`; finished steps are no-ops.

# Exposure

> What is reachable from the LAN, over NetBird, and from the internet — and how to make a service public or private.

Every service is LAN-only by default: the Cloudflare wildcard `*.madhan.app` points at the private Gateway IP. A service becomes public only when it is listed in `publicServices` in [`cloudflare.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/cloudflare.go). ## How it fits [Section titled “How it fits”](#how-it-fits) 
```
flowchart LR
  subgraph DNS[Cloudflare, DNS-only]
    W["*.madhan.app → 192.168.1.220"]
    P["public names → 178.156.199.250"]
  end
  W --> G[Cilium Gateway]
  P --> T[Traefik on Bifrost] -->|ForwardAuth unless SkipAuth| N[NetBird tunnel] --> G
```
 All records are DNS-only (not proxied). A specific record beats the wildcard, so deleting a service’s record is all it takes to make it private again: its name falls back to `192.168.1.220`, which the internet cannot reach. ## What is reachable where [Section titled “What is reachable where”](#what-is-reachable-where) | Name or address | LAN | VPN (NetBird) | Public | | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | ------------- | ----------------------------------------------------- | | `auth`, `netbird`, `uptime`, `proxy`, `*.proxy` | Yes | Yes | Yes, served by Bifrost itself | | `grafana` | Yes | Yes | Yes, Grafana’s own Authentik login (`SkipAuth: true`) | | `argocd`, `hubble` (Pulumi HTTPRoutes) | Yes | Yes | No | | `longhorn`, `openbao`, `harbor`, `n8n`, `headlamp`, `falco`, `vmselect`, `alertmanager`, `victorialogs`, `kubeflow`, `ollama`, `comfyui`, `chat`, `home`, `adguard` | Yes | Yes | No | | `192.168.1.225:11434` (Ollama LoadBalancer) | Yes | Yes | No | | `192.168.1.226:53` (AdGuard DNS LoadBalancer) | Yes | Yes | No | | `192.168.1.230` (CS2 LoadBalancer) | Yes | Yes | No | Hostnames are `<name>.madhan.app`. VPN reach comes from the `192.168.1.0/24` route that `k8s-routing-peer` advertises to the `All` group; the public wildcard record makes the same names resolve off-LAN. ComfyUI ships scaled to zero. ## Make a service public [Section titled “Make a service public”](#make-a-service-public) 1. Add it to `publicServices` in [`cloudflare.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/cloudflare.go). Set `SkipAuth: true` only if the app does its own Authentik login. core/cloud/cloudflare.go 
   ```diff
   var publicServices = []PublicService{
       {Name: "grafana", SkipAuth: true},
   +    {Name: "headlamp"},
   }
   ```
 2. Run `just core hetzner up`. It regenerates `traefik/dynamic/public-services.yml` (gitignored) and Traefik hot-reloads the router. 3. Run `just core cloudflare up` to create the A record pointing at `178.156.199.250`. 4. Check: `dig +short headlamp.madhan.app` returns `178.156.199.250`, and an unauthenticated `curl -I https://headlamp.madhan.app` redirects to `auth.madhan.app`. To make it private again, remove the entry and run the same two commands. Never edit `public-services.yml` or `services.yml` for this; the first is regenerated on every run. ## Temporary sharing [Section titled “Temporary sharing”](#temporary-sharing) `netbird expose <port>` from any mesh peer publishes `<name>.proxy.madhan.app` through Traefik TCP passthrough and `netbird-proxy`, without DNS changes and without Authentik. See [NetBird](/cloud/netbird/). ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) ### A service is still public after removing it [Section titled “A service is still public after removing it”](#a-service-is-still-public-after-removing-it) The A record still exists: run `just core cloudflare up`. Resolvers may cache the old answer until its TTL expires. ### Public name resolves but returns 504 [Section titled “Public name resolves but returns 504”](#public-name-resolves-but-returns-504) Traefik has the route but cannot reach the Gateway. See [Bifrost troubleshooting](/cloud/bifrost/).

# NetBird

> WireGuard mesh that carries Bifrost and remote devices into the LAN, with embedded Dex OIDC federated to Authentik.

The NetBird server on Bifrost coordinates a WireGuard mesh; an in-cluster routing peer advertises `192.168.1.0/24`, so Bifrost’s Traefik and any enrolled laptop or phone reach LAN services. [NetBird docs](https://docs.netbird.io/). | | | | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Server | `netbird.madhan.app` on [Bifrost](/cloud/bifrost/) | | Peers | `bifrost-agent` (Docker on Bifrost), `k8s-routing-peer` (StatefulSet, namespace `netbird`) | | Source | [`netbird/config.yaml`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/bifrost/netbird/config.yaml), [`bootstrap.sh`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/bifrost/bootstrap.sh), [`netbird_peer.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/networking/netbird_peer.go) | | Auth | Embedded Dex, Authentik as upstream connector | ## How it fits [Section titled “How it fits”](#how-it-fits) 
```
flowchart LR
  L[Laptop / phone] -->|WireGuard| P
  T[Traefik] --> S[netbird-server<br/>management, signal,<br/>relay, Dex]
  B[bifrost-agent] <-->|WireGuard| P[k8s-routing-peer<br/>pod network]

Peer details live on [NetBird peer](/workloads/networking/netbird-peer/). ### Embedded Dex is the issuer [Section titled “Embedded Dex is the issuer”](#embedded-dex-is-the-issuer) The combined server always runs embedded Dex, so every JWT NetBird validates is signed by Dex. `auth.issuer` must stay `https://netbird.madhan.app/oauth2`; pointing it at Authentik makes Dex claim Authentik’s identity while signing with its own keys, and logins fail with `unable to find appropriate key`. Authentik is a connector inside Dex, added in the UI. ## Configuration [Section titled “Configuration”](#configuration) | Setting | Value | Why | | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | | `auth.issuer` | `https://netbird.madhan.app/oauth2` | Embedded Dex; see above | | Dashboard client | `netbird-dashboard`, public, no secret | Hard-coded static client in Dex | | `reverseProxy.trustedHTTPProxies` | `172.30.0.10/32` | Traefik’s fixed IP in `bifrost_net` | | `store.engine` | `sqlite`, encrypted with `NB_DATA_STORE_KEY` | | | `dataDir` | `/var/lib/netbird` | Peer and server state; see the caution below | | Traefik routers | gRPC (`/signalexchange…`, `/management…`) as h2c; `/relay`, `/ws-proxy/`, `/api`, `/oauth2` as HTTP; everything else to the dashboard | Defined in [`services.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/bifrost/traefik/dynamic/services.yml) | | STUN | UDP 3478, published by `netbird-server` | Bypasses Traefik | NetBird does not expand variables in config.yaml The file is read verbatim. `bootstrap.sh` substitutes `${NB_RELAY_SECRET}` and `${NB_DATA_STORE_KEY}` with `sed`, and `${NB_OWNER_HASH}` (a bcrypt hash of `NB_OWNER_PASSWORD`) with Python, because the hash contains `$` and `/`. Verify from Bifrost: 
   ```sh
   ssh root@178.156.199.250 'docker exec netbird-agent netbird routes list'   # 192.168.1.0/24 Selected
   ssh root@178.156.199.250 'curl -s -o /dev/null -w "%{http_code}\n" -H "Host: grafana.madhan.app" http://192.168.1.220/'
   ```
 ## Operate [Section titled “Operate”](#operate) 
```sh

```

# Secrets model

> Two tiers — SOPS and age for bootstrap secrets, OpenBao plus the Secrets Store CSI driver for everything at runtime.

Bootstrap secrets are what the platform needs before OpenBao exists; they live age-encrypted in git. Every other secret lives in OpenBao and reaches pods through the Secrets Store CSI driver. Why two tiers: [Two-tier secrets](/reference/decisions/secrets-two-tier/). 
```
flowchart LR
    subgraph BOOT["Bootstrap tier"]
        SOPS["secrets/bootstrap.sops.yaml<br/>age-encrypted, in git"]
        CS["just create-secrets"]
        PU["just core STACK up"]
        KS["k8s Secrets<br/>Prune=false"]
        ENV["Bifrost env files"]
    end
    subgraph RUN["Runtime tier"]
        OB["OpenBao<br/>KV v2 at secret/"]
        CSI["Secrets Store CSI<br/>+ OpenBao provider"]
        F["File at /mnt/secrets/KEY"]
        S["Synced k8s Secret"]
    end
    SOPS --> CS --> KS
    SOPS --> PU --> ENV
    KS -->|unseal key| OB
    OB -->|Kubernetes auth<br/>per-app role| CSI
    CSI --> F
    CSI -->|secretObjects,<br/>while mounted| S
```
 ## Bootstrap tier: SOPS and age [Section titled “Bootstrap tier: SOPS and age”](#bootstrap-tier-sops-and-age) `secrets/bootstrap.sops.yaml` holds the provider tokens, the Authentik and NetBird keys for Bifrost, and the OpenBao unseal key. Recipes decrypt it per command with `sops exec-env`; nothing decrypted is written to the repo. Pulumi passes the Bifrost keys into one env file per container (see [Bifrost](/cloud/bifrost/)). [`create-bootstrap-secrets.sh`](https://github.com/madhank93/homelab/blob/v0.1.8/scripts/create-bootstrap-secrets.sh), run by `just create-secrets`, creates the only two in-cluster bootstrap Secrets: | Secret | Namespace | Used by | | ---------------------- | -------------- | ---------------------------------------------- | | `openbao-unseal-key` | `openbao` | The OpenBao unseal sidecar | | `cloudflare-api-token` | `cert-manager` | DNS-01 challenges for the wildcard certificate | Both carry `argocd.argoproj.io/sync-options: Prune=false`, so Argo CD never deletes Secrets it did not create. ## Runtime tier: OpenBao and the CSI driver [Section titled “Runtime tier: OpenBao and the CSI driver”](#runtime-tier-openbao-and-the-csi-driver) Each app has a SecretProviderClass, built by `kit.SecretProviderClass` in [`kit.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/kit/kit.go). It reads keys from `secret/data/<app>` using the OpenBao Kubernetes auth role of the same name, bound to the app’s ServiceAccount. `just openbao-setup` creates the auth method, policies and roles once; see [OpenBao](/workloads/secrets/openbao/) and [Secrets Store CSI Driver](/workloads/secrets/csi-driver/). | Pattern | When | Apps | | ------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | | File only | The app can read a value from a file; no Secret object exists | Grafana admin password (`$__file{}` in an env var) | | Synced Secret | The chart wants an `existingSecret` or the app reads only env vars | Grafana OIDC client secret, Harbor, n8n, NetBird peer, Falco (Sidekick UI), CS2, Homepage, Headlamp | Prefer file-only: the value never appears in `kubectl get secret`. The CSI mount is what creates the Secret A SecretProviderClass fetches nothing on its own, and `secretObjects` creates nothing until a running pod mounts the CSI volume. Charts that cannot add volumes (Harbor, Falco) get a `secret-sync` pause pod from `kit.SecretSync` whose only job is to hold that mount open. “The Secret was never created” almost always means no pod mounts the volume. ## Unsealing OpenBao [Section titled “Unsealing OpenBao”](#unsealing-openbao) OpenBao seals itself on every restart. An `unseal` container in `extraContainers` ([`openbao.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/secrets/openbao.go)) reads `openbao-unseal-key` and loops `bao operator unseal` against `127.0.0.1:8200`. It is a sidecar, not an init container, because unseal requests need the server already running. The very first initialisation is manual: `just openbao-init`. ## Rules [Section titled “Rules”](#rules) | Rule | Enforced by | | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Workload code declares no `Secret` objects | Convention in `workloads/`; secrets come from OpenBao | | No new Secret payload in published manifests | CI [`manifest-secret-guard.sh`](https://github.com/madhank93/homelab/blob/v0.1.8/scripts/manifest-secret-guard.sh); its [allowlist](https://github.com/madhank93/homelab/blob/v0.1.8/scripts/manifest-secret-allowlist.txt) of chart-rendered Secrets may only shrink | | No root token at rest | `just openbao-root` generates one per command from the unseal key and revokes it on exit | | CI needs no repository secrets beyond its own `GITHUB_TOKEN` | Synthesis reads nothing secret |

> The three paths into the cluster — public internet through Bifrost, LAN direct to the Gateway, and NetBird VPN — down to the packet.

Every path ends at the same Cilium Gateway (`192.168.1.220`); they differ in how a packet reaches it. DNS decides which path a hostname takes. Follow one request Press Play or Step · click any box for details −Reset+⛶ × #### [Read more →]() ## DNS split [Section titled “DNS split”](#dns-split) Cloudflare holds the records, all DNS-only (not proxied). Source: [`cloudflare.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/cloudflare.go). | Record | Points to | Path | | ----------------------------------------------- | ------------------------------- | -------------------------------- | | `*.madhan.app` | `192.168.1.220` (Gateway LB IP) | LAN or VPN only | | `auth`, `netbird`, `proxy`, `uptime`, `*.proxy` | `178.156.199.250` (Bifrost) | Served by containers on the VPS | | each entry in `publicServices` | `178.156.199.250` (Bifrost) | Public, tunnelled to the cluster | To make a cluster service public, add it to `publicServices`; see [Service exposure](/cloud/exposure/). ### Home DNS [Section titled “Home DNS”](#home-dns) Devices set by hand to use [AdGuard Home](/workloads/networking/adguard/) send every lookup to its LoadBalancer IP; AdGuard drops ad and tracker domains and resolves the rest, `*.madhan.app` included, over DNS-over-HTTPS. ```
flowchart LR
    C[Device with DNS<br/>192.168.1.226] -->|UDP/TCP 53| N[Node holding<br/>the L2 lease]
    N -->|Cilium DNAT| A[AdGuard pod<br/>one of two]

 ## The three paths [Section titled “The three paths”](#the-three-paths) * Public internet Traefik on Bifrost terminates TLS and proxies plain HTTP to `http://192.168.1.220`. The host’s NetBird agent routes the LAN subnet into the WireGuard mesh, so that address is reachable from the VPS. 
  ```
  sequenceDiagram
      actor C as Client
      participant DNS as Cloudflare DNS
      participant TR as Traefik<br/>Bifrost :443
      participant BA as bifrost-agent<br/>wt0 (host network)
      participant WG as WireGuard<br/>(direct or relay)
      participant NP as k8s-routing-peer<br/>netbird-peer pod, wt0
      participant ETH as Gateway node<br/>eth0 + Cilium BPF
      participant EN as Envoy<br/>(Gateway)
      participant P as Backend pod

      C->>DNS: grafana.madhan.app?
      DNS-->>C: 178.156.199.250
      C->>TR: HTTPS
      Note over TR: TLS terminated<br/>ForwardAuth unless SkipAuth
      TR->>BA: HTTP to 192.168.1.220:80
      Note over BA: route 192.168.1.0/24 via wt0
      BA->>WG: encrypted
      WG->>NP: decapsulated on wt0
      Note over NP: forward wt0 → pod eth0<br/>MASQUERADE: src → pod IP
      NP->>ETH: LAN, dst 192.168.1.220
      Note over ETH: node holding the L2 lease answers ARP<br/>Cilium DNAT to Envoy
      ETH->>EN: HTTP

      P-->>C: reply retraces the path<br/>(conntrack undoes NAT)
  ```
 | Hop | Detail | Source | | ---------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | | Traefik | File provider only; public routers are generated into `public-services.yml` from `publicServices` | [`hetzner.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/hetzner.go) | | bifrost-agent | `netbird-agent` container, `network_mode: host`, peer name `bifrost-agent` | [`docker-compose.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/core/cloud/bifrost/docker-compose.yml) | | k8s-routing-peer | `netbird-peer` StatefulSet in pod networking, no `nodeSelector`: it runs on whichever worker the scheduler picks | [`netbird_peer.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/networking/netbird_peer.go) | | MASQUERADE | Init container adds `POSTROUTING ! -o wt0 -d 192.168.1.0/24 -j MASQUERADE` | [`netbird_peer.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/networking/netbird_peer.go) | | Cilium | Datapath on `ens18`/`eth0` only; L2 announcement of the LB pool | [`cilium.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/cilium.go) | Replies need no route back to the overlay. MASQUERADE rewrites the source to the peer’s pod IP, Cilium load-balances the packet from the pod’s `eth0` (so it works on the L2 lease holder too), and conntrack in the pod reverses the NAT and returns the reply into `wt0`. Nodes carry only a default route ([`talos.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/talos.go)), which is why the peer can float between workers. Never add wt0 to Cilium devices `wt0` is a NOARP/POINTOPOINT WireGuard interface with no Ethernet header. Cilium’s TC BPF program expects Ethernet frames, so on `wt0` it misparses every packet and drops it without a single monitor event, and the public path dies silently. Packets from `wt0` must instead leave through the kernel to the LAN NIC of the node that owns the Gateway IP, where Cilium runs on a real Ethernet interface. * LAN A LAN client resolves `*.madhan.app` to `192.168.1.220` and talks to the Gateway directly — no VPS, no ForwardAuth. 
  ```
  flowchart LR
      C[LAN client] -->|DNS: 192.168.1.220| N[Node holding<br/>the L2 lease]
      N -->|Cilium DNAT| E[Envoy<br/>Gateway :80 / :443]
      E -->|HTTPRoute| P[Backend pod]
  ```
 The Gateway `homelab-gateway` (namespace `kube-system`) listens on HTTP `:80` and HTTPS `:443`; HTTPS terminates with the wildcard certificate from [cert-manager](/platform/cert-manager/). Cilium hands out LB addresses from `192.168.1.220`–`230`, skipping any that are node IPs. A public service resolves to Bifrost even on the LAN, so LAN clients hairpin through the VPS unless local DNS overrides the record — see [Service exposure](/cloud/exposure/). * VPN (NetBird) A NetBird client anywhere joins the mesh through `netbird.madhan.app`, which is served on Bifrost. The k8s-routing-peer advertises `192.168.1.0/24`, so the client reaches the Gateway and every LAN-only hostname as if it were at home. 
  ```
  flowchart LR
      C[NetBird client] -->|WireGuard| NP[k8s-routing-peer<br/>wt0]
      NP -->|forward + MASQUERADE| G[Gateway<br/>192.168.1.220]
      G --> P[Backend pod]
  ```
 The route is assigned to the peer in the NetBird UI, not in code. The datapath from `wt0` onward is the same as the public path. See [NetBird](/cloud/netbird/). ## When the public path breaks [Section titled “When the public path breaks”](#when-the-public-path-breaks) A 504 from a public URL means Traefik is up but cannot reach the Gateway. The runbook is on [NetBird peer](/workloads/networking/netbird-peer/).

# GPU

> The RTX 5070 Ti on k8s-worker4 — passthrough, the dedicated=ai taint, time-slicing, and what every GPU pod needs.

An NVIDIA RTX 5070 Ti (16 GB VRAM) is passed through to `k8s-worker4` and shared by Ollama, ComfyUI and Kubeflow. [Device plugin docs](https://github.com/NVIDIA/k8s-device-plugin). | | | | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Node | `k8s-worker4` · `192.168.1.224` | | PCIe ID | `0000:09:00.0` (`pcie_ids` in [`config.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/config/config.yml)) | | Namespace | `nvidia-gpu-operator` | | Source | [`nvidia_gpu_operator.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/hardware/nvidia_gpu_operator.go), [`talos.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/talos.go) | ## How it fits [Section titled “How it fits”](#how-it-fits) The driver and container toolkit come from Talos system extensions in the GPU image. In the cluster, the [NVIDIA device plugin](/workloads/hardware/nvidia-device-plugin/) advertises the card, time-slices it and exports DCGM metrics; its settings (RuntimeClass, NVML discovery, time-slicing) are documented there. Proxmox passes the card with `pcie: true` and `xvga: false`: it is compute-only, and VGA BAR constraints conflict with large memory allocations. Passthrough changes need a cold boot of the VM. ## Configuration [Section titled “Configuration”](#configuration) | Setting | Value | Why | | ---------- | ------------------------- | ----------------------------------------------------------- | | Node taint | `dedicated=ai:NoSchedule` | Keeps ordinary pods off the GPU node’s CPU during inference | ## Scheduling a GPU pod [Section titled “Scheduling a GPU pod”](#scheduling-a-gpu-pod) Every GPU pod needs all of these. Device plugin and DCGM Exporter already carry them. 
```yaml
runtimeClassName: nvidia            # without it CUDA is invisible in the container
nodeSelector:
  nvidia.com/gpu.present: "true"    # set by GPU Feature Discovery
tolerations:                        # the selector alone will not pass the taint
  - key: dedicated
    operator: Equal
    value: ai
    effect: NoSchedule
resources:
  limits:
    nvidia.com/gpu: 1
env:
  - name: NVIDIA_VISIBLE_DEVICES
    value: all
```
 Missing runtimeClassName fails quietly The pod schedules and gets `nvidia.com/gpu`, yet CUDA sees no device. Kubeflow notebooks need it too. Five slices, one 16 GB pool Time-slicing shares GPU time, not memory, and nothing in Kubernetes limits VRAM. ComfyUI keeps its model in VRAM after a run, so with both running Ollama fails to load a model and the error shows up on the Ollama side. ComfyUI ships scaled to zero; turn it on only when needed and off afterwards. ## Operate [Section titled “Operate”](#operate) 
```sh
just comfyui on     # commits the replica change; Argo CD selfHeal reverts kubectl scale
just comfyui off    # the only reliable way to free ComfyUI's VRAM


# Evict Ollama's loaded model without a restart
curl https://ollama.madhan.app/api/generate -d '{"model": "<model>", "keep_alive": 0}'


kubectl get pods -n nvidia-gpu-operator
kubectl describe node k8s-worker4 | grep nvidia.com/gpu
```
 GPU utilisation, VRAM, temperature and power come from DCGM Exporter through its ServiceMonitor; look for the DCGM dashboard in Grafana. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) ### GPU pod stuck Pending with no obvious reason [Section titled “GPU pod stuck Pending with no obvious reason”](#gpu-pod-stuck-pending-with-no-obvious-reason) The pod lacks the `dedicated=ai` toleration, or `nvidia.com/gpu` is exhausted. Add the toleration; check `kubectl describe node k8s-worker4` for allocated GPUs. ### Ollama cannot load a model while ComfyUI is running [Section titled “Ollama cannot load a model while ComfyUI is running”](#ollama-cannot-load-a-model-while-comfyui-is-running) ComfyUI holds the VRAM. Run `just comfyui off`. ### Pod runs but `nvidia-smi` or CUDA finds no device [Section titled “Pod runs but nvidia-smi or CUDA finds no device”](#pod-runs-but-nvidia-smi-or-cuda-finds-no-device) `runtimeClassName: nvidia` is missing. Add it and recreate the pod.

# Repairs

> The just recipes and one-liners that fix known failure modes, and when to run each.

Each recipe below fixes a failure this cluster has actually hit. Run them from the repo root on a laptop with cluster access. Full recipe list: [justfile reference](/reference/justfile/). ## Recipes [Section titled “Recipes”](#recipes) | Recipe | When to run | What it does | | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `just gateway-repair-l2` | LAN times out on the Gateway IP while in-cluster requests to it still succeed, typically after a Cilium agent restart | Checks port 80 on the Gateway LoadBalancer IP; if unreachable, deletes its `cilium-l2announce-…` lease to force re-election, then waits up to a minute for recovery | | `just longhorn-repair-iscsi` | No Longhorn volume on a node attaches after a Talos upgrade; volumes cycle `faulted` | In every instance-manager pod, enters the host `iscsid` namespaces, reads the parameter `iscsiadm` rejects, and strips it from `/var/lib/iscsi/nodes/`. Idempotent; `just talos-upgrade` runs it for you | | `just comfyui on` / `off` | Before using ComfyUI; afterwards, to free VRAM for Ollama | Rewrites the `// comfyui-replicas` literal in [`comfyui.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/ai/comfyui.go), runs `just synth`, commits and pushes. Git is the only place a scale sticks: Argo CD self-heal reverts `kubectl scale` | | `just argocd-sync <app>` | Auto-sync is paused (`argocd_manual_sync: true`) or one app needs a sync now | Patches the Application with a sync operation (prune, `CreateNamespace`, `ServerSideApply`); no `argocd` CLI needed | | `just talos-health` | Before and after any node change; must be clean before the next node | `talosctl health` against the first control plane via the VIP | | `just talos-versions` | Checking an upgrade landed on every node | `talosctl version` on every node in `config/config.yml` | | `just headlamp-token [duration]` | Logging in to Headlamp | Issues a short-lived cluster-admin token for `headlamp-admin` (default 24h) | | `just openbao-root <bao args>` | You need root on OpenBao | Generates a root token over the in-pod unix socket from the unseal key Secret, runs one `bao` command with it, revokes it on exit. Piped stdin reaches `bao`, for `key=-` values | | `just openbao-get <path> [field]` | Reading one secret | Mints a throwaway root token, reads the KV path, revokes the token on exit | | `just openbao-sa-get <sa> <ns> <role> <path> [field]` | Proving an app’s role can read its secret | Logs in with the service account’s token through Kubernetes auth, then reads the path | | `just grafana-init` | Grafana fails to start because provisioning references org 2 | Creates Grafana’s “Public” org and checks it got id 2. Idempotent | | `just ping_scan` | Finding what is alive on the LAN | `nmap -sn` over the cluster subnet | ## Without a recipe [Section titled “Without a recipe”](#without-a-recipe) ### Failed DaemonSet pods after DiskPressure [Section titled “Failed DaemonSet pods after DiskPressure”](#failed-daemonset-pods-after-diskpressure) Pods evicted under DiskPressure stay `Failed`, and the DaemonSet does not replace them once the pressure clears, so Longhorn and the CSI driver stay down on that node. 
```bash
kubectl get pods -A --field-selector=status.phase=Failed
kubectl delete pods -A --field-selector=status.phase=Failed
```
 ### Stale L2 lease on a Service other than the Gateway [Section titled “Stale L2 lease on a Service other than the Gateway”](#stale-l2-lease-on-a-service-other-than-the-gateway) `gateway-repair-l2` covers only the Gateway. Delete the lease of any other LoadBalancer Service that answers in-cluster but not from the LAN: 
```bash
kubectl delete lease -n kube-system cilium-l2announce-<namespace>-<service>
```
 ### Node hangs on reboot [Section titled “Node hangs on reboot”](#node-hangs-on-reboot) A node with a broken Cilium datapath cannot reboot gracefully: unmounting a Longhorn RWX volume blocks on a share-manager ClusterIP it can no longer reach. Skip the graceful path: 
```bash
talosctl --talosconfig ~/.talos/config reboot --nodes <ip> --mode powercycle
```
 If the Talos API is dead too, reset the VM from Proxmox. Re-check the Gateway afterwards: a restarted agent is when a stale L2 lease appears. ### RWO volume deadlocked during a rollout [Section titled “RWO volume deadlocked during a rollout”](#rwo-volume-deadlocked-during-a-rollout) The new pod waits on a volume the old pod still holds. Force-delete the old pod, or scale its old ReplicaSet to zero: 
```bash
kubectl scale replicaset <old-rs> -n <namespace> --replicas=0
```

# Argo CD

> Bump the Argo CD chart and the image pinned ahead of it, applied by Pulumi.

Phase 3. Risk: medium, GitOps pauses while the server restarts. Pins: `charts.argo-cd` and `images.argocd` in [`config/versions.yaml`](https://github.com/madhank93/homelab/blob/v0.1.8/config/versions.yaml), read by [`argocd.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/argocd.go). config/versions.yaml 
```yaml
charts:
  argo-cd: {repo: https://argoproj.github.io/argo-helm, version: X.Y.Z}
images:
  argocd: {image: quay.io/argoproj/argocd, tag: vX.Y.Z}
```
 **Image ahead of chart.** The Release overrides `image.tag` to run a server newer than the chart pins. On every chart bump, check whether the chart’s appVersion has caught up and drop the override once it has. 
```bash
just core platform preview
just core platform up
kubectl rollout status deployment argocd-server -n argocd
kubectl get applications -n argocd   # all Synced + Healthy
```
 To roll out a large change one app at a time, set `argocd_manual_sync: true` in `config/config.yml`, apply, sync with `just argocd-sync <app>`, then set it back to `false` and apply again.

```bash

# Talos and Kubernetes

> Rolling Talos node upgrades with just talos-upgrade, then the separate Kubernetes rollout and Pulumi apply.

Phase 1. Risk: high, every node reboots. Pins: `talos` and `kubernetes` in [`config/versions.yaml`](https://github.com/madhank93/homelab/blob/v0.1.8/config/versions.yaml). config/versions.yaml 
```yaml
talos: {version: vX.Y.Z, base_schematic: …, gpu_schematic: …}

```
 ## Rules [Section titled “Rules”](#rules) * One Talos minor at a time (1.12 → 1.13, never 1.12 → 1.15). * Control planes first, one at a time, then workers, then the GPU worker last. Gate on health between nodes. * Schematic IDs hash only the extension list, so they survive a version bump. Check every extension still exists for the new release: `curl -s https://factory.talos.dev/version/vX.Y.Z/extensions/official | jq -r '.[].name'`. * Kubernetes is pinned on its own line and must stay inside Cilium’s supported range. When it moves a minor, update `k8s@X.Y.Z` in `workloads/cdk8s.yaml` and [regenerate imports](/operate/upgrades/cdk8s-imports/). * Use a `talosctl` client of 1.14.1 or later; 1.14.0 can hang the full timeout after a node is already back. Never lower talos.version and run just core talos up On a downgrade the provider regenerates the cluster secrets (new PKI). `talos-secrets` is protected, so the run fails instead — but do not try. Roll nodes back with `talosctl rollback` and leave the pin alone. just core talos up does not upgrade a running node Images download to a fixed filename, so the Proxmox file ID never changes and existing disks keep their old Talos. Only new VMs get the new image. Upgrade nodes with `just talos-upgrade`. ## `just talos-upgrade` [Section titled “just talos-upgrade”](#just-talos-upgrade) 
```bash
just talos-upgrade 192.168.1.223            # worker, base schematic
just talos-upgrade 192.168.1.224 gpu        # GPU worker
just talos-upgrade 192.168.1.224 gpu false  # skip the drain
```
 The recipe refuses the wrong schematic for a node (`pcie_ids` in `config/config.yml` marks the GPU worker), asks before rebooting, waits for `talosctl health`, then runs `just longhorn-repair-iscsi`. Never pass `--preserve`: it forces the deprecated MachineService upgrade path, whose metal installer rejects these configs. Drain deadlock Longhorn gives each instance-manager a PDB allowing zero disruptions while a volume is attached, and a single-instance CNPG cluster (`n8n-pg`) can never release its only pod. The drain burns its timeout and `talosctl` exits **before** rebooting, leaving the node cordoned and un-upgraded. Pass `drain=false` for the GPU worker and for whichever worker hosts `n8n-pg-1` (`kubectl get pod -n n8n n8n-pg-1 -o wide`). If it already happened: re-run with `false`, then `kubectl uncordon <node>`. ## Runbook [Section titled “Runbook”](#runbook) 1. Check the starting point. 
   ```bash
   kubectl config use-context admin@talos-cluster
   talosctl version --client --short
   just talos-versions
   just talos-health
   ```
 2. Upgrade the control planes, one at a time. Talos refuses an upgrade that breaks etcd quorum. 
   ```bash
   just talos-upgrade 192.168.1.211
   just talos-upgrade 192.168.1.212
   just talos-upgrade 192.168.1.213
   ```
 3. Upgrade the workers. Prove Longhorn attaches on the first before doing the rest. Public traffic drops while the node running `netbird-peer-0` reboots. 
   ```bash
   just talos-upgrade 192.168.1.223
   just talos-upgrade 192.168.1.222
   just talos-upgrade 192.168.1.221
   ```
 4. Upgrade the GPU worker last: it gets a new NVIDIA driver build, and its PDBs need `drain=false`. 
   ```bash
   just talos-upgrade 192.168.1.224 gpu false
   talosctl --talosconfig ~/.talos/config -n 192.168.1.224 get extensions          # nvidia-* present
   kubectl get node k8s-worker4 -o jsonpath='{.status.allocatable.nvidia\.com/gpu}'  # 5
   ```
 5. Roll out Kubernetes. It never rides along with a Talos upgrade, and must run before `just core talos up`, which would otherwise push new images to every node at once. 
   ```bash
   just talos-upgrade-k8s --dry-run
   just talos-upgrade-k8s
   ```
 6. Preview, then apply Pulumi. 
   ```bash
   just core talos preview
   just core talos up
   ```
 The preview should show updates only: `talos-secrets` (version contract), the two image downloads, and the per-node config applies. **A `replace` on `talos-secrets` or any VM means stop.** ### Gate before every next node [Section titled “Gate before every next node”](#gate-before-every-next-node) 
```bash
just talos-health                                      # clean
kubectl get nodes                                      # all Ready, none SchedulingDisabled
talosctl --talosconfig ~/.talos/config -n 192.168.1.211,192.168.1.212,192.168.1.213 etcd status

  -o custom-columns=NAME:.metadata.name,ROBUSTNESS:.status.robustness | grep -E 'degraded|faulted'
                                                       # empty: replicas rebuilt
```
 An undrained reboot can wait about ten minutes on a Longhorn CSI unmount. It finishes by itself. ## After each node: iSCSI records [Section titled “After each node: iSCSI records”](#after-each-node-iscsi-records) An upgrade can ship an open-iscsi that rejects a parameter its predecessor wrote into `/var/lib/iscsi/nodes/`. `iscsiadm` reads every record, so one bad file fails the whole call and no Longhorn volume on that node can attach; Longhorn marks the volume faulted and retries forever. The records sit on persistent `/var`, so a reboot does not clear them. `just talos-upgrade` runs `just longhorn-repair-iscsi` for this; run it standalone any time. ## If a node will not come back [Section titled “If a node will not come back”](#if-a-node-will-not-come-back) A node whose Cilium datapath does not recover cannot reboot gracefully: unmounting a Longhorn RWX volume blocks on an NFS share-manager ClusterIP it can no longer reach, so `talosctl reboot` hangs at `unmountPodMounts`. `cri` and `kubelet` read `Finished/Fail` while the Talos API stays up. Power-cycle instead: 
```bash
talosctl --talosconfig ~/.talos/config reboot --nodes <ip> --mode powercycle
```
 ## Rollback [Section titled “Rollback”](#rollback) Before `just core talos up`: `talosctl rollback --nodes <ip>` boots the previous A/B image with data intact, then revert the commit. After it, roll nodes back with `talosctl rollback` and never lower the pin. ## Talos 1.13 → 1.14 notes [Section titled “Talos 1.13 → 1.14 notes”](#talos-113--114-notes) * Talos 1.14 defaults to Kubernetes 1.37, which Cilium does not support yet, so `kubernetes.version` holds the cluster on 1.36. * Upgraded nodes keep their v1alpha1 config. The deprecated fields this repo sets (`machine.install`, `machine.kernel`, `machine.nodeLabels`, `machine.nodeTaints`, `machine.kubelet.nodeIP`) still work. * 1.14-only defaults such as workload isolation (`SecurityProfileConfig`) and periodic trim stay off. Leave workload isolation off: it moves the kubelet and pods into a sandbox PID namespace, and Longhorn’s iSCSI frontend and `just longhorn-repair-iscsi` reach into the host `iscsid` namespaces.

# Control plane HA

> Three control planes share the Talos VIP 192.168.1.210 — failover, not load balancing, and what one lost node costs.

Three control planes run etcd and the API server; a Talos-managed VIP floats between them so every client uses one address. [Talos VIP docs](https://www.talos.dev/latest/talos-guides/network/vip/). | | | | ------ | ------------------------------------------------------------------------------------------------- | | Nodes | `k8s-controller1`–`3` · `192.168.1.211`–`213` | | VIP | `192.168.1.210:6443` | | Source | [`talos.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/talos.go) (`cpPatch`) | ## How it fits [Section titled “How it fits”](#how-it-fits) One controller holds the VIP and answers ARP for it; if it dies, another takes over within seconds. Only the holder serves API traffic: this is failover, not load balancing. The built-in VIP was chosen because it needs no extra VM or keepalived, and the API server’s load is small. etcd needs a majority: with three members the cluster survives one loss. Losing two blocks all writes. ## During a failover [Section titled “During a failover”](#during-a-failover) * New API connections succeed once another node announces the VIP; in-flight requests to the dead node fail. * `kubectl` sees a few seconds of errors, then recovers. * Running pods are unaffected; kubelets keep them running without the API server. * Cilium reaches the API server through the VIP (`k8sServiceHost`), so it follows the failover. Pulumi bootstraps etcd on the first control plane in `config.yml` (`k8s-controller1`); the others join it. ## Operate [Section titled “Operate”](#operate) 
```sh
talosctl --talosconfig ~/.talos/config etcd members --nodes 192.168.1.211
talosctl --talosconfig ~/.talos/config get addresses --nodes 192.168.1.211,192.168.1.212,192.168.1.213   # VIP holder shows .210
kubectl cluster-info
```
 Reboot control planes one at a time and wait for etcd to report three healthy members before the next. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) ### API unreachable on the VIP but the nodes are up [Section titled “API unreachable on the VIP but the nodes are up”](#api-unreachable-on-the-vip-but-the-nodes-are-up) Check which node holds `192.168.1.210` with the `get addresses` command above. If none does, check etcd membership on each controller: the VIP is only announced by a node whose etcd is healthy.

# Cilium for networking

> Why one Cilium install replaces kube-proxy, MetalLB and an Ingress controller.

**Decision:** Cilium as CNI with kube-proxy replacement, L2 announcements for LoadBalancer IPs, and its Gateway API implementation for all HTTP routing. **Context:** Bare metal has no cloud load balancer, Talos ships no CNI here, and every app needs hostname routing behind one IP the wildcard DNS record can point at. | Option | For | Against | | ---------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | | Cilium (CNI + L2 + Gateway API) | One component; eBPF datapath; Hubble flow visibility; Gateway API role split | Talos-specific tuning (`hostLegacyRouting`, socket LB off); restarts can leave stale L2 leases | | Flannel/Calico + MetalLB + ingress-nginx | Familiar, widely documented | Three components to version; Ingress has no Gateway/route split | | Ingress API instead of Gateway API | Simpler, every chart supports it | HTTP only, limited matching, no infra/app separation | **Consequences:** * Gateway API CRDs are vendored and applied before Cilium; Cilium upgrades go one minor at a time. * `wt0` can never be a Cilium device, so the NetBird peer keeps `wt0` in its pod netns and reaches Cilium through the pod’s `eth0`. * An L2 lease can go stale after an agent restart; `just gateway-repair-l2` re-elects it.

# CloudNativePG for app databases

> Why n8n's Postgres is a CloudNativePG Cluster rather than the Bitnami subchart bundled with its Helm chart.

**Decision:** Run application Postgres as CloudNativePG `Cluster` resources in each app’s namespace; disable bundled database subcharts. **Context:** n8n’s chart bundles a Bitnami Postgres subchart. Its password would have to come from chart values or OpenBao, and its lifecycle is tied to n8n’s chart. | Option | For | Against | | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | | **CloudNativePG operator** | Database upgrades independently of the app; operator generates and owns the credentials (`<name>-app` Secret); scales to replicas and backups through one resource | One more operator to run | | Bitnami subchart | Nothing extra to install | Password lives in values or a hand-made Secret; upgrades ride the app chart | **Consequences:** * The database password is the one app credential not in OpenBao. * n8n’s cluster is a single instance, so there is no failover yet. * A major Postgres bump needs a new cluster or `pg_upgrade`.

# GitOps with Pulumi and CDK8s

> Why infrastructure runs from a laptop with Pulumi while workloads go through CDK8s, CI and Argo CD from a release manifests branch.

**Decision:** Pulumi (Go) for VMs, cluster, platform and edge, run only from a laptop. CDK8s (Go) for workloads, synthesized in CI to a `<release>-manifests` branch that Argo CD syncs. **Context:** Infrastructure changes can destroy VMs, DNS or the Gateway and need bootstrap secrets; workload changes are frequent, reviewable and safe to reconcile continuously. The repository is public. | Option | For | Against | | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- | | Pulumi everywhere, from CI | One tool, one pipeline | CI would need every bootstrap secret; a bad merge could destroy infrastructure | | Helm or Kustomize files synced directly | No synthesis step | Untyped YAML; shared values (domain, gateway, OpenBao address) repeated per app | | Pulumi on a laptop + CDK8s through CI (chosen) | Typed Go on both sides sharing `config/config.yml`; CI holds no secrets; Argo CD shows and heals drift | Two toolchains; workloads see a change only after CI publishes | **Consequences:** * A human runs every `just core <stack> up`; nothing in CI can change infrastructure. * The cluster runs whatever `manifests_branch` in `config/config.yml` names, so a release is rolled out by changing one line and running `just core platform up`. * Synthesized manifests are public, so CI blocks any new rendered Secret payload.

# Harbor for the registry

> Why Harbor over a plain Docker registry for private images and pull-through caching.

**Decision:** Harbor, on the LAN only, behind the shared Gateway. **Context:** The cluster needs somewhere to push its own images and a local cache for Docker Hub and GHCR pulls. | Option | For | Against | | -------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- | | **Harbor** | Projects and RBAC, pull-through proxy cache, built-in vulnerability scanning, web UI | Many components (core, portal, registry, jobservice, database, Redis); its own admin account | | Docker Distribution (`registry`) | One small container | No RBAC, scanning or UI; caching one upstream per instance | **Consequences:** * Its chart cannot mount extra volumes, so a `secret-sync` pod is needed to get the admin password from OpenBao. * Registry and jobservice PVCs are RWX to avoid Multi-Attach deadlocks on rollouts.

# Kubeflow without Istio

> Why Kubeflow runs without Istio, Knative, KServe and Dex, and what replaces them.

**Decision:** Install Kubeflow’s notebooks, pipelines, Katib, Trainer and Spark Operator from the upstream manifests, without Istio, Knative, KServe or Dex. **Context:** Cilium already provides the Gateway, network policy and L7 visibility, and identity is handled at the Bifrost edge. Upstream Kubeflow assumes Istio for routing and auth. | Component | Decision | Reason | | ------------------ | -------- | ------------------------------------------------------------------------------------------- | | Istio | Excluded | Cilium covers the mesh features in use; a second data plane doubles the networking to debug | | Knative | Excluded | No serverless workloads | | KServe | Excluded | Ollama serves the models in use | | Dex / oauth2-proxy | Excluded | Single user; the route injects `kubeflow-userid` | **Consequences:** * Stub Istio CRDs keep controllers that watch Istio kinds from crashing, and a kustomize patch strips every Istio resource and upstream NetworkPolicy. * The [notebook gateway controller](/workloads/ai/notebook-gateway-controller/) replaces the per-notebook VirtualServices with HTTPRoutes. * No authentication: anyone on the LAN is `user@example.com`. Multi-user access needs an OIDC proxy.

# Longhorn for storage

> Why replicated storage on the workers' OS disks beat Rook-Ceph, NFS and local-path.

**Decision:** Longhorn, 3 replicas across the 4 workers, as the default StorageClass. **Context:** The workers are Proxmox VMs with one OS disk each and no spare block devices, and stateful apps must survive losing a node. | Option | For | Against | | ------------ | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | | **Longhorn** | Uses part of each OS disk; RWX through a built-in NFS share-manager; UI for volumes and snapshots | Single vendor; replicas share disk I/O with the OS | | Rook-Ceph | Feature-rich, scales well | Needs dedicated disks per node; heavy for 4 small workers | | NFS server | Simple | Single point of failure, no replication | | local-path | No overhead | Data is tied to one node | **Consequences:** * Capacity is limited by OS disk free space, so scheduling relies on 300% overprovisioning. * `longhorn-manager` must stay off control-plane nodes, or engine images never finish deploying and attaches block. * Talos upgrades can leave iSCSI records that block attaches; `just longhorn-repair-iscsi` clears them.

# Two-tier secrets

> Why bootstrap secrets live in SOPS and age while runtime secrets live in OpenBao behind the Secrets Store CSI driver.

**Decision:** SOPS with age for the few secrets needed before the cluster can serve secrets; OpenBao with the Secrets Store CSI driver for everything else. **Context:** The repository and its manifests branch are public, so no plaintext secret may reach git. OpenBao runs in the cluster, so it cannot hold the secrets that build the cluster or unseal OpenBao itself. | Option | For | Against | | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | | Everything in SOPS | No in-cluster service to run | Every app secret becomes a k8s Secret in rendered manifests; rotation needs a commit | | Everything in OpenBao | One store | Chicken-and-egg: Pulumi and the unseal step need secrets before OpenBao exists | | SOPS for bootstrap + OpenBao at runtime (chosen) | Bootstrap set stays small and reproducible from git; app secrets never appear in manifests and can be mounted as files | Two systems; OpenBao must be unsealed after every restart | **Consequences:** * Losing the age private key means losing the bootstrap secrets; back it up outside the repository. * Each app needs a SecretProviderClass and an OpenBao role, and a pod must mount the CSI volume for a synced Secret to exist. * The unseal key sits in a k8s Secret so a sidecar can unseal OpenBao unattended.

# VictoriaMetrics and VictoriaLogs

> Why metrics and logs go to single-node VictoriaMetrics and VictoriaLogs rather than Prometheus and Loki.

**Decision:** VictoriaMetrics single-node (VMSingle) for metrics and VictoriaLogs single-node for logs, both read by Grafana. **Context:** The cluster runs many workloads on limited RAM and on Longhorn disks shared by every volume. The stores must accept Prometheus remote write and OTLP, and work with Grafana’s stock Prometheus and Loki datasources. | Option | For | Against | | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | | **VictoriaMetrics + VictoriaLogs** | Several times less memory and disk than Prometheus; long retention built in; PromQL-compatible (MetricsQL); one vendor’s operator, CRDs and naming | Grafana reads logs through the Loki plugin, which VictoriaLogs implements only partly (no volume API) | | Prometheus + Loki | Reference implementations; widest ecosystem | Higher memory; long-term storage needs Thanos or Cortex; Loki adds object storage or more components | | VMCluster (insert/select/storage) | Horizontal scale | Three components to run for one cluster’s worth of metrics | **Consequences:** * The Grafana VictoriaLogs datasource needs `logsVolumeEnabled: false` and a URL ending at `/select`. * ServiceMonitor and PrometheusRule CRDs are installed by hand so app charts’ monitors still work; VMOperator converts them. * One VMSingle is a single point of failure for metrics.

# Docs site

> How these docs are built with Astro Starlight, linked, kept honest about versions, deployed and written.

[Astro Starlight](https://starlight.astro.build/) in `docs/`; pages are Markdown or MDX under `docs/src/content/docs/`, and the URL follows the path (`workloads/storage/longhorn.md` → `/workloads/storage/longhorn/`). 
```bash
just docs-serve    # npm run dev, http://localhost:4321, live reload
just docs-check    # version and link guard, same as CI
```
 Run `npm ci` in `docs/` once first. ## Links [Section titled “Links”](#links) * **Internal:** absolute with a trailing slash, `/platform/cilium/`. [starlight-links-validator](https://github.com/HiDeoo/starlight-links-validator) fails the build on a broken page or anchor. * **Source:** ``[`cilium.go`](src:core/platform/cilium.go)``. A remark plugin ([`remark-src-links.mjs`](https://github.com/madhank93/homelab/blob/v0.1.8/docs/src/plugins/remark-src-links.mjs)) rewrites `src:` to the file on GitHub at the `ref` constant in [`astro.config.mjs`](https://github.com/madhank93/homelab/blob/v0.1.8/docs/astro.config.mjs). The path must be git-tracked; `app/` never is. ## Versions [Section titled “Versions”](#versions) Versions live only in the [Software inventory](/reference/software-inventory/). `just docs-check` ([`docs-version-check.sh`](https://github.com/madhank93/homelab/blob/v0.1.8/scripts/docs-version-check.sh)) fails when: * an inventory version no longer appears in the file its row names; * any other page states a version (`operate/upgrades/` and `releases/` are exempt); * a page names a manifests branch other than `manifests_branch` in `config/config.yml`; * a `src:` link points at an untracked file; * a Mermaid label uses `\n` instead of `<br/>`. A version that is a historical fact, not a claim about what runs, is allowed on a line ending in `<!-- docs-check: historical -->` (`{/* docs-check: historical */}` in MDX). ## Deploy [Section titled “Deploy”](#deploy) [`.github/workflows/docs.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/.github/workflows/docs.yml) runs on pushes to `main` and `v*` branches that touch docs, config or code. Both run the check and build; **only release branches deploy** `docs/dist` to `gh-pages`, so the live site matches the `ref` in `astro.config.mjs`. On a release cut, move together: `ref` in `astro.config.mjs`, `manifests_branch` in `config/config.yml`, and any inventory row that changed. ## Writing style [Section titled “Writing style”](#writing-style) * Short: present tense, active voice; runbooks imperative (“Run”, “Check”). No “we”, no marketing, no emoji. * Only homelab-specific facts: one sentence on what a component does here, then a link to upstream. No “What is X?” sections. * Tables for facts, prose for reasons; a reason is one sentence. Sentence-case headings; description ≤ 160 chars. * Component pages follow: summary → at-a-glance table (namespace, source, exposure, storage, auth) → how it fits → configuration (non-default settings only) → operate → troubleshooting (symptom headings). Drop empty sections. * “Why X over Y” goes in a decision page under `reference/decisions/`; the component page keeps one sentence and a link. * Asides: `danger` for data loss or outage, `caution` for surprising failure, `tip`, `note`. Use `<Steps>` for procedures of three or more steps, `<Tabs>` only for parallel alternatives. Rename to `.mdx` only when using a component.

See [Talos](/operate/upgrades/talos/). 3. **Kubernetes**, then Pulumi: `just talos-upgrade-k8s`, `just core talos preview` (stop on any replace), `just core talos up`. 4. **Gateway API CRDs, then Cilium 1.19.10, then 1.20.4** as three applies with the four gates between each. See [Cilium](/operate/upgrades/cilium/). 5. **Argo CD and cert-manager**: `just core platform up` on unmodified HEAD. 6. **Grafana org**: `just grafana-init` before the Grafana change syncs. Then set `argocd_manual_sync: true` and apply. 7. **Repoint Argo CD** to `v0.1.8-manifests`, `just argocd-sync openbao`, delete `openbao-0` (OnDelete), then `just openbao-setup`. Sync Falco now. 8. **Workloads by risk** with `just argocd-sync <app>`: low → storage (CNPG, then Longhorn) → observability → Ollama → Kubeflow (delete `jobset-controller-manager` and `profiles-deployment`) → n8n → CS2. 9. **Verify Falco**, then set `argocd_manual_sync: false` and apply. 10. **Bifrost**: `just core hetzner preview` (no server replace), then `up`. 11. **Pulumi providers** (cloudflare v6, proxmoxve v8): preview every stack and stop on any VM or DNS record replace. Open after rollout k8s-worker1 host DNS is flaky; each Cilium agent rollout darkens the Gateway IP for about 35 s; after a control-plane restart a new HTTPRoute can stay status-less until the Cilium operator leader pod is deleted; there is no Longhorn backup target. Ollama with flash attention on Blackwell may crash at warmup ([ollama/ollama#18276](https://github.com/ollama/ollama/issues/18276)) — set `OLLAMA_FLASH_ATTENTION=0` if it does. Harbor keeps its existing admin password; rotate it and update OpenBao. Deferred: Kubernetes 1.37, SSO in front of every UI, default-deny NetworkPolicies, Kyverno enforce mode, image digest pins, NetBird 0.81.x.

# Prerequisites

> Install the tools, create the age key, and fill the SOPS file every later phase reads.

Goal: a laptop that can decrypt `secrets/bootstrap.sops.yaml`, and a file that holds every Phase 0 key. ## Requirements [Section titled “Requirements”](#requirements) | Need | Detail | | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | | Proxmox host | Room for 32 vCPU, 82 GiB RAM and 1000 GiB disk across seven VMs; API access as `root@pam`; an NVIDIA GPU to pass through to `k8s-worker4` | | Accounts | Hetzner Cloud, Cloudflare (zone for `madhan.app`), a GitHub OAuth app for Authentik | | Tools | `pulumi`, `talosctl`, `kubectl`, `just`, `sops`, `age`, `go`, `yq`, `jq`, `cdk8s` — all in the [devcontainer](/reference/development/devcontainer/) | VM sizes come from `cluster.nodes` in [`config.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/config/config.yml); the Go toolchain is pinned in [`.mise.toml`](https://github.com/madhank93/homelab/blob/v0.1.8/.mise.toml). ## Procedure [Section titled “Procedure”](#procedure) 1. Install the tools, or open the devcontainer: 
   ```sh
   brew install pulumi talosctl kubectl just sops age go yq jq
   npm install -g cdk8s-cli
   ```
 2. Create the age key and export its path. sops does not find the key file on its own. 
   ```sh
   mkdir -p ~/.config/sops/age
   age-keygen -o ~/.config/sops/age/keys.txt
   echo 'export SOPS_AGE_KEY_FILE="$HOME/.config/sops/age/keys.txt"' >> ~/.zshrc
   ```
 3. Put the public key in [`.sops.yaml`](https://github.com/madhank93/homelab/blob/v0.1.8/.sops.yaml) under `creation_rules[*].age`. 4. Open the secrets file. sops decrypts it in your editor and re-encrypts on save. 
   ```sh
   just sops-view secrets/bootstrap.sops.yaml
   ```
 5. Add every key below. Generate random values with the command shown. secrets/bootstrap.sops.yaml (keys only) 
   ```yaml
   PROXMOX_PASSWORD:              # Proxmox root password
   HCLOUD_TOKEN:                  # Hetzner Cloud API token
   CLOUDFLARE_API_TOKEN:          # Zone:DNS edit — cert-manager and Traefik ACME
   AUTHENTIK_TOKEN:               # openssl rand -hex 30; becomes the akadmin API token
   AUTHENTIK_SECRET_KEY:          # openssl rand -base64 48
   AUTHENTIK_POSTGRESQL_PASSWORD: # openssl rand -hex 16
   AUTHENTIK_GITHUB_SECRET:       # GitHub OAuth app secret
   GRAFANA_OAUTH_CLIENT_SECRET:   # openssl rand -hex 32
   ARGOCD_OAUTH_CLIENT_SECRET:    # openssl rand -hex 32
   HARBOR_OAUTH_CLIENT_SECRET:    # openssl rand -hex 32
   HOMEPAGE_OAUTH_CLIENT_SECRET:  # openssl rand -hex 32
   KUBERNETES_OAUTH_CLIENT_SECRET: # openssl rand -hex 32; Headlamp and kube-apiserver OIDC
   PROXMOX_OAUTH_CLIENT_SECRET:   # openssl rand -hex 32
   NETBIRD_CLIENT_SECRET:         # openssl rand -hex 32
   NB_DATA_STORE_KEY:             # openssl rand -base64 32
   NB_RELAY_SECRET:               # openssl rand -base64 32
   NB_OWNER_PASSWORD:             # first NetBird login only
   OPENBAO_UNSEAL_KEY: placeholder   # real value in Phase 2
   NB_BIFROST_SETUP_KEY: placeholder # real value in Phase 6
   ```
 Back up the age key `~/.config/sops/age/keys.txt` is the only way to decrypt the secrets file. Lose it and every SOPS value must be regenerated, including `NB_DATA_STORE_KEY`. NB_DATA_STORE_KEY is permanent It encrypts the NetBird database. Changing it after the first deploy loses every peer registration. NB_BIFROST_SETUP_KEY needs a value now `hetzner.go` refuses to run while it is empty, but the real key only exists after Phase 6. A placeholder gets Phase 3 through; `netbird-agent` cannot join the mesh until it is replaced. ## Check [Section titled “Check”](#check) 
```sh
sops -d secrets/bootstrap.sops.yaml >/dev/null && echo decrypts
```
 `decrypts` means the key and `.sops.yaml` match. Never print the decrypted output.

# Initialise OpenBao

> Initialise and unseal OpenBao, store the unseal key in SOPS, then configure Kubernetes auth and seed app secrets.

Goal: OpenBao unsealed and auto-unsealing, with a policy, a role and seeded secrets for every app. About 10 minutes. ## Procedure [Section titled “Procedure”](#procedure) 1. Wait for the OpenBao pod to run. It stays sealed. 
   ```sh
   kubectl get pods -n openbao -w
   ```
 2. Initialise and unseal. The recipe revokes the init root token at once and writes only the unseal key, to `~/openbao-unseal-key` (mode 600). 
   ```sh
   just openbao-init
   ```
 3. Set `OPENBAO_UNSEAL_KEY` in SOPS to the contents of that file. 
   ```sh
   just sops-view secrets/bootstrap.sops.yaml
   ```
 4. Push the real key into the cluster and restart the pod. The StatefulSet uses `OnDelete`, so a rollout does nothing; the unseal sidecar reads the new Secret on start. 
   ```sh
   just create-secrets
   kubectl delete pod -n openbao openbao-0
   rm ~/openbao-unseal-key
   ```
 5. Enable Kubernetes auth and KV v2, write a read-only policy and role per app, and seed every missing key. 
   ```sh
   just openbao-setup
   ```
 `openbao-setup` is idempotent: it rewrites auth, policies and roles, but never overwrites a key that exists. The OAuth client secrets come from SOPS: `GRAFANA_OAUTH_CLIENT_SECRET` → `secret/grafana`, `HARBOR_OAUTH_CLIENT_SECRET` → `secret/harbor`, `HOMEPAGE_OAUTH_CLIENT_SECRET` → `secret/homepage` and `KUBERNETES_OAUTH_CLIENT_SECRET` → `secret/headlamp`. Everything else is random. `NETBIRD_SETUP_KEY` starts as a placeholder so the CSI mount succeeds, and gets its real value in [Phase 6](/start/deploy/6-netbird-keys/). openbao-init refuses to run twice It stops if `~/openbao-unseal-key` exists. Move the key into SOPS and delete the file first. openbao-setup stops on a missing SOPS key It exits if any of `GRAFANA_OAUTH_CLIENT_SECRET`, `HARBOR_OAUTH_CLIENT_SECRET`, `HOMEPAGE_OAUTH_CLIENT_SECRET` or `KUBERNETES_OAUTH_CLIENT_SECRET` is missing from the SOPS file. Add it (see [Phase 0](/start/deploy/0-prerequisites/)) and re-run. ## Check [Section titled “Check”](#check) 
```sh
kubectl exec -n openbao openbao-0 -c openbao -- bao status | grep Sealed
just openbao-sa-get grafana grafana grafana secret/grafana ADMIN_PASSWORD >/dev/null && echo policy-ok
kubectl get applications -n argocd
```
 `Sealed false`, then `policy-ok`. Apps turn `Healthy` as their CSI volumes mount. Details: [Secrets](/concepts/secrets/), [OpenBao](/workloads/secrets/openbao/).

# NetBird keys and route

> Create the setup keys and proxy token, redeploy Bifrost, give the cluster its routing-peer key, and route the LAN.

Goal: Bifrost and the cluster peer join the mesh, and Bifrost reaches `192.168.1.0/24` through it. About 5 minutes. ## Procedure [Section titled “Procedure”](#procedure) 1. In the NetBird UI, logged in through GitHub, create two reusable keys under **Setup Keys → Add Key**, and one token under **Settings → Access Tokens → Create Personal Access Token**. | Item | Stored as | | ---------------------------- | ----------------------------------------------- | | Setup key `bifrost-agent` | `NB_BIFROST_SETUP_KEY` in SOPS | | Setup key `k8s-routing-peer` | `NETBIRD_SETUP_KEY` in OpenBao `secret/netbird` | | Personal access token | `NB_PROXY_TOKEN` in SOPS | 2. Add `NB_BIFROST_SETUP_KEY` (replacing the placeholder) and `NB_PROXY_TOKEN` to SOPS, then redeploy. The bootstrap now starts `netbird-agent` and `netbird-proxy`. 
   ```sh
   just sops-view secrets/bootstrap.sops.yaml
   just core hetzner up
   ```
 3. Write the cluster key to OpenBao. The key travels on stdin, so it never shows in a process list. 
   ```sh
   printf '%s' '<k8s-routing-peer key>' | just openbao-root kv patch -mount=secret netbird NETBIRD_SETUP_KEY=-
   ```

   ```sh
   kubectl delete pod -n netbird netbird-peer-0
   ```
 5. In the NetBird UI, add **Network → Routes → Add Route**: network `192.168.1.0/24`, routing peer `k8s-routing-peer`, enabled. Never set NB_SKIP_SOCKET_MARK on the peer The routing peer adds a host route that keeps management traffic off WireGuard; the socket mark is what bypasses it. ```sh

```

# NetBird peer

> In-cluster WireGuard routing peer that lets Bifrost reach the cluster LAN.

`k8s-routing-peer` joins the NetBird mesh and routes the cluster LAN to Bifrost, so Traefik there can proxy public services to the Gateway. Mesh and Bifrost side: [NetBird](/cloud/netbird/). [Upstream docs](https://docs.netbird.io/). | | | | --------- | ---------------------------------------------------------------------------------------------------------- | | Namespace | `netbird` (privileged PSA) | | Source | [`netbird_peer.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/networking/netbird_peer.go) | | Exposure | None; it is the path for public traffic | | Storage | `netbird-config` PVC, 100 Mi RWO, at `/var/lib/netbird/` | | Auth | `NETBIRD_SETUP_KEY` from OpenBao `secret/netbird`, first registration only | ## How it fits [Section titled “How it fits”](#how-it-fits) 
```
sequenceDiagram
  participant T as Traefik (Bifrost)
  participant A as bifrost-agent wt0
  participant P as netbird-peer-0 (any worker)
  participant G as Gateway 192.168.1.220
  T->>A: proxy to 192.168.1.220:80
  A->>P: WireGuard via relay
  P->>P: forward wt0 → pod eth0,<br/>MASQUERADE to pod IP
  P->>G: Cilium load-balances from the pod
  G-->>P: reply to the pod IP
  P-->>A: back through wt0
```
 The StatefulSet has **no nodeSelector**; the pod runs on whichever worker schedules it. Because `wt0` lives in the pod’s own network namespace, forwarded traffic leaves through the pod’s `eth0` and Cilium load-balances it like any pod traffic, wherever the Gateway’s L2 lease is. With `hostNetwork` the peer depended on ARP for `192.168.1.220`, which fails when the peer shares a node with the lease holder: a node cannot resolve the IP it announces itself. The MASQUERADE rule means backends see the pod IP, so no node needs a route to the NetBird overlay. No such route exists in [`talos.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/talos.go); nodes get only a default route via the router. ## Configuration [Section titled “Configuration”](#configuration) | Setting | Value | Why | | ------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | | Kind | StatefulSet, 1 replica | Stable identity with its PVC | | PVC mount | `/var/lib/netbird/` | NetBird keeps its private key there; without it every restart registers a duplicate peer | | `hostNetwork` | `false` (default) | `wt0` and its routes stay in the pod netns; see above | | Capabilities | `NET_ADMIN`, `SYS_MODULE`, privileged | WireGuard and iptables | | Image | `netbird` in [`config.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/config/config.yml) | Must match the Bifrost server; see [Software inventory](/reference/software-inventory/) | | `NB_MANAGEMENT_URL` | `https://netbird.madhan.app` | Management server on Bifrost | | `NB_HOSTNAME` | `k8s-routing-peer` | Name the NetBird route is assigned to | | Reloader | `reloader.stakater.com/auto` | Restarts when the setup-key Secret changes | The cluster subnet route is **not** set in code. Assign it in the NetBird UI: **Network → Routes**, network `192.168.1.0/24`, routing peer `k8s-routing-peer`, distribution group `All`. ### MASQUERADE initContainer [Section titled “MASQUERADE initContainer”](#masquerade-initcontainer) `setup-iptables` runs before the agent: 
```bash
iptables -t nat -C POSTROUTING ! -o wt0 -d 192.168.1.0/24 -j MASQUERADE 2>/dev/null \
  || iptables -t nat -A POSTROUTING ! -o wt0 -d 192.168.1.0/24 -j MASQUERADE
```
 It matches “not back out `wt0`” rather than a NIC name. `-C` stops restarts from stacking duplicates. While the route’s **Masquerade** toggle is on in the NetBird UI, NetBird’s own `NETBIRD-RT-NAT` chain matches first and this rule counts 0 packets; it is the fallback if that toggle is ever turned off. Never set NB_SKIP_SOCKET_MARK The peer adds a host route for the management server via `lo`; socket fwmark lets its own traffic bypass it. Without the mark, management traffic loops into the tunnel, the relay never connects, and `wt0` carries 0 bytes: every public service goes down. Details: [NetBird](/cloud/netbird/). Keep wt0 out of Cilium devices `wt0` is NOARP/POINTOPOINT; Cilium’s TC BPF drops its frames silently. [`cilium.go`](https://github.com/madhank93/homelab/blob/v0.1.8/core/platform/cilium.go) lists only `ens18` and `eth0`. See [Cilium](/platform/cilium/). ## Operate [Section titled “Operate”](#operate) 
```bash
kubectl get pods -n netbird -o wide           # which worker it landed on
kubectl exec -n netbird netbird-peer-0 -c netbird -- netbird status
```
 Expect `Management: Connected` and `Networks: 192.168.1.0/24`. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) ### Peer not connecting [Section titled “Peer not connecting”](#peer-not-connecting) Check logs, then that the management URL answers from the pod:

# Longhorn

> Replicated block storage on the workers' OS disks; the cluster's default StorageClass.

Longhorn replicates every volume across three workers, so a PVC survives losing its node. [Upstream docs](https://longhorn.io/docs/). | | | | --------- | ----------------------------------------------------------------------------------------------- | | Namespace | `longhorn-system` (privileged PSA) | | Source | [`longhorn.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/storage/longhorn.go) | | Exposure | LAN · `longhorn.madhan.app` → `longhorn-frontend:80` | | Storage | `/var/lib/longhorn/` on each worker’s OS disk | | Auth | None | Longhorn was chosen because it needs no dedicated disks; see [Longhorn for storage](/reference/decisions/longhorn/). ## How it fits [Section titled “How it fits”](#how-it-fits) 
```
flowchart LR
  pod[Pod] --> pvc[PVC<br/>storageClass longhorn]
  pvc --> csi[Longhorn CSI]
  csi --> mgr[longhorn-manager]
  mgr --> r1[Replica<br/>worker A]
  mgr --> r2[Replica<br/>worker B]
  mgr --> r3[Replica<br/>worker C]
  pvc -. RWX .-> sm[share-manager<br/>NFS pod]
```
 RWX volumes get a Longhorn share-manager pod that serves NFS, so several pods (or an old and new pod during a rollout) can mount the same volume. ## Configuration [Section titled “Configuration”](#configuration) | Setting | Value | Why | | ------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------- | | `defaultReplicaCount`, `defaultClassReplicaCount` | `3` | Three of the four workers hold each volume | | `storageOverProvisioningPercentage` | `300` | 200% ran out of schedulable space for 50 Gi AI model replicas | | `defaultDataPath` | `/var/lib/longhorn/` | Persistent path on Talos | | `createDefaultDiskLabeledNodes` | `false` | Every node gets a default disk, no labels needed | | `concurrentAutomaticEngineUpgradePerNodeLimit` | `1` | Volumes move to the new engine image after an upgrade, one per node at a time | | `preUpgradeChecker.jobEnabled` | `false` | The pre-upgrade hook does not fit Argo CD sync | | `networkPolicies.metricsScrapeSources` | `vmagent` in `victoria-metrics` | The chart’s NetworkPolicies otherwise block cross-namespace scrapes of `longhorn-manager:9500` | | Driver and UI tolerations | control-plane `NoSchedule` | Driver and UI may run on control planes; the manager may not | Never let longhorn-manager tolerate the control-plane taint Each manager pod registers its node as a Longhorn node, and each Longhorn node needs an engine image. The engine-image DaemonSet tolerates only the `taintToleration` setting (`dedicated=ai`), so control-plane nodes would leave EngineImages stuck “deploying” and **every volume attach in the cluster blocks**. `longhornManager` tolerates `dedicated=ai` and nothing else. ### Capacity [Section titled “Capacity”](#capacity) Disk sizes come from [`config.yml`](https://github.com/madhank93/homelab/blob/v0.1.8/config/config.yml). Longhorn shares each disk with the OS and container images. | Node | Disk | | ----------------- | ------- | | k8s-worker1–3 | 200 GiB | | k8s-worker4 (GPU) | 250 GiB | ## Operate [Section titled “Operate”](#operate) 
```bash
kubectl get volumes.longhorn.io -n longhorn-system \
  -o custom-columns=NAME:.metadata.name,STATE:.status.state,ROBUSTNESS:.status.robustness
```
 Healthy volumes show `attached` / `healthy`. After a Talos upgrade, run `just longhorn-repair-iscsi` (the `talos-upgrade` flow already calls it). ![Longhorn volume list showing attached volumes and replica health](/assets/screenshots/longhorn/volume-list.png) ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) ### Volumes stuck attaching after a node upgrade [Section titled “Volumes stuck attaching after a node upgrade”](#volumes-stuck-attaching-after-a-node-upgrade) An open-iscsi upgrade can reject a parameter in an old record under `/var/lib/iscsi/nodes/`, which fails every attach on that node. Run `just longhorn-repair-iscsi`. ### Volume stuck attaching, PVC Pending, or pod in ContainerCreating [Section titled “Volume stuck attaching, PVC Pending, or pod in ContainerCreating”](#volume-stuck-attaching-pvc-pending-or-pod-in-containercreating) Check the volume and, for RWX, its share-manager pod: 
```bash
kubectl describe pvc <pvc> -n <namespace>
kubectl get pods -n longhorn-system | grep share-manager
```
 If one volume is wedged, detach it in the Longhorn UI, then force-delete the pod. If **every** attach is stuck, check EngineImages first (see the danger aside above): `kubectl get engineimages -n longhorn-system`. ### `ROBUSTNESS=degraded` [Section titled “ROBUSTNESS=degraded”](#robustnessdegraded) A replica’s node is down or out of space. Longhorn rebuilds on another worker once it can schedule; check node status first. ### `Multi-Attach error for volume` [Section titled “Multi-Attach error for volume”](#multi-attach-error-for-volume) An RWO volume is still attached to the old pod’s node during a rollout. Scale down the old ReplicaSet and force-delete the stuck pod; [Harbor](/workloads/registry/harbor/#multi-attach-error-on-a-rollout) has the steps. The lasting fix is `ReadWriteMany`.

# Reloader

> Rolls workloads when a ConfigMap or Secret they reference changes.

Reloader watches ConfigMaps and Secrets and rolls any annotated workload that uses them, which is how rotated OpenBao values reach running pods. [Upstream docs](https://github.com/stakater/Reloader). | | | | --------- | ----------------------------------------------------------------------------------------------- | | Namespace | `reloader` | | Source | [`reloader.go`](https://github.com/madhank93/homelab/blob/v0.1.8/workloads/support/reloader.go) | | Exposure | None | | Storage | — | | Auth | — | Reloader runs with chart defaults; opt in per workload on the **pod template**: 
```go
"podAnnotations": map[string]any{
    "reloader.stakater.com/auto": "true",
},
```
 Annotated today: Grafana, OpenBao, NetBird peer, Falco and its Sidekick UI, every `secret-sync` pod (Harbor, Falco), the OpenTelemetry collectors, the notebook gateway controller, Homepage, CS2, and AdGuard Home. ## How it fits [Section titled “How it fits”](#how-it-fits) 
```
flowchart LR
  bao[OpenBao value changes] --> csi[CSI driver<br/>polls every 2m]
  csi --> sec[Mirrored Secret updated]
  sec --> rl[Reloader]
  rl --> roll[Rolling restart<br/>of annotated workload]
```
 ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) ### Workload not restarting [Section titled “Workload not restarting”](#workload-not-restarting) The annotation is on the Deployment’s metadata instead of `spec.template.metadata`, or the app reads its value as a file with no mirrored Secret behind it. 
```bash
