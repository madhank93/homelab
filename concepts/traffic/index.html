How traffic flows

Every path ends at the same Cilium Gateway (192.168.1.220); they differ in how a packet reaches it. DNS decides which path a hostname takes.

DNS split

Section titled “DNS split”

Cloudflare holds the records, all DNS-only (not proxied). Source: cloudflare.go.

RecordPoints toPath
*.madhan.app192.168.1.220 (Gateway LB IP)LAN or VPN only
auth, netbird, proxy, uptime, *.proxy178.156.199.250 (Bifrost)Served by containers on the VPS
each entry in publicServices178.156.199.250 (Bifrost)Public, tunnelled to the cluster

To make a cluster service public, add it to publicServices; see Service exposure.

The three paths

Section titled “The three paths”
  • Public internet
  • LAN
  • VPN (NetBird)

Traefik on Bifrost terminates TLS and proxies plain HTTP to http://192.168.1.220. The host’s NetBird agent routes the LAN subnet into the WireGuard mesh, so that address is reachable from the VPS.

    actor C as Client
    participant DNS as Cloudflare DNS
    participant TR as Traefik<br/>Bifrost :443
    participant BA as bifrost-agent<br/>wt0 (host network)
    participant WG as WireGuard<br/>(direct or relay)
    participant NP as k8s-routing-peer<br/>netbird-peer pod, wt0
    participant ETH as Gateway node<br/>eth0 + Cilium BPF
    participant EN as Envoy<br/>(Gateway)
    participant P as Backend pod

    DNS-->>C: 178.156.199.250
    C->>TR: HTTPS
    Note over TR: TLS terminated<br/>ForwardAuth unless SkipAuth
    TR->>BA: HTTP to 192.168.1.220:80

    WG->>NP: decapsulated on wt0

Replies need no route back to the overlay. MASQUERADE rewrites the source to the peer’s pod IP, Cilium load-balances the packet from the pod’s eth0 (so it works on the L2 lease holder too), and conntrack in the pod reverses the NAT and returns the reply into wt0. Nodes carry only a default route (talos.go), which is why the peer can float between workers.

Never add wt0 to Cilium devices

wt0 is a NOARP/POINTOPOINT WireGuard interface with no Ethernet header. Cilium’s TC BPF program expects Ethernet frames, so on wt0 it misparses every packet and drops it without a single monitor event, and the public path dies silently. Packets from wt0 must instead leave through the kernel to the LAN NIC of the node that owns the Gateway IP, where Cilium runs on a real Ethernet interface.

A LAN client resolves *.madhan.app to 192.168.1.220 and talks to the Gateway directly — no VPS, no ForwardAuth.

flowchart LR
    C[LAN client] -->|DNS: 192.168.1.220| N[Node holding<br/>the L2 lease]
    N -->|Cilium DNAT| E[Envoy<br/>Gateway :80 / :443]
    E -->|HTTPRoute| P[Backend pod]

The Gateway homelab-gateway (namespace kube-system) listens on HTTP :80 and HTTPS :443; HTTPS terminates with the wildcard certificate from cert-manager. Cilium hands out LB addresses from 192.168.1.220–230, skipping any that are node IPs.

A public service resolves to Bifrost even on the LAN, so LAN clients hairpin through the VPS unless local DNS overrides the record — see Service exposure.

A NetBird client anywhere joins the mesh through netbird.madhan.app, which is served on Bifrost. The k8s-routing-peer advertises 192.168.1.0/24, so the client reaches the Gateway and every LAN-only hostname as if it were at home.

flowchart LR
    C[NetBird client] -->|WireGuard| NP[k8s-routing-peer<br/>wt0]
    NP -->|forward + MASQUERADE| G[Gateway<br/>192.168.1.220]
    G --> P[Backend pod]

The route is assigned to the peer in the NetBird UI, not in code. The datapath from wt0 onward is the same as the public path. See NetBird.

When the public path breaks

Section titled “When the public path breaks”

A 504 from a public URL means Traefik is up but cannot reach the Gateway. The runbook is on NetBird peer.
