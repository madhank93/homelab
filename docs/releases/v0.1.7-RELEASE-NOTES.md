## Bug Fixes

### Talos upgrades were impossible — `machine.install` was being deleted

**Root cause:** nodes boot `talos.platform=metal` despite nocloud factory
images, and the metal installer refuses to upgrade without `machine.install`.
`patchTalosConfig` in `core/platform/talos.go` had been deleting that section
since Feb 2026, so no node ever carried one. Every upgrade failed with
`install instructions are required in metal mode`.

**Fix:** `basePatch` declares `install.disk: /dev/sda` and the unconditional
delete is gone. sda is the 215 GB virtio system disk; sdb is Longhorn storage
and is never an install target.

**File:** `core/platform/talos.go`

---

### `--preserve` forced the deprecated upgrade path

Talos 1.13 upgrades via LifecycleService, which preserves data and drains the
node itself. Passing `--preserve` forced the old MachineService.Upgrade
fallback.

**File:** justfile (`talos-upgrade` recipe)

---

### Optional drain skip for nodes that cannot be evicted

Longhorn gives each instance-manager a PDB allowing zero disruptions while a
volume is attached, and a single-instance CNPG cluster's PDB can never release
its only pod. The drain burns its timeout, `talosctl` exits before rebooting,
and the node is left cordoned on the old version. `just talos-upgrade <ip>
[base|gpu] [drain]` now takes an explicit drain toggle.

**File:** justfile

---

### Longhorn — control-plane toleration deadlocked all volume attachment

**Root cause:** `longhornManager.tolerations` carried the control-plane taint,
so a manager pod ran on each control plane and registered it as a Longhorn
node. Every registered node must then have the engine image deployed, but
engine-image DaemonSets receive only the global `defaultSettings.taintToleration`
(empty here) and schedule on workers only. EngineImages stalled at
`Engine image is not fully deployed on all nodes: 4 of 7`, state `deploying`,
and **no volume in the cluster could attach**.

**Fix:** dropped the toleration. Control planes hold no Longhorn disks and run
no PVC-backed pods. `longhornDriver` and `longhornUI` tolerations are retained —
those are Deployments and do not register Longhorn nodes.

**File:** `workloads/storage/longhorn.go`

This fix was cherry-picked to `v0.1.6` as `e4aea57` and applied ahead of this
release because it was resolving a live outage.

---

### Wildcard TLS — duplicate Certificate exhausted the Let's Encrypt rate limit

**Root cause:** two Certificates requested the same identifier set
(`madhan.app`, `*.madhan.app`): `kube-system/wildcard-madhan-app` and a second
one in `cilium-secrets` that existed only to hand Envoy's SDS a copy, because
Cilium's `gatewayAPI.secretsNamespace.sync` was disabled. `cilium-secrets` is
Cilium's own namespace, so the foreign secret kept being removed and
cert-manager kept re-issuing it — 72 revisions. That tripped Let's Encrypt's
limit of 5 certificates per exact identifier set per 168h:

```
429 rateLimited: too many certificates (5) already issued for this exact set
of identifiers in the last 168h0m0s
```

With no secret in `cilium-secrets`, the Gateway's HTTPS listener had no
certificate and **every `*.madhan.app` HTTPS endpoint reset the connection**,
while plain HTTP through the same Gateway kept returning 200.

**Fix:** one Certificate, one owner for the copy. `secretsNamespace.sync` is
back on, so Cilium mirrors `kube-system/wildcard-madhan-app-tls` into
`cilium-secrets` itself, and the duplicate Certificate is deleted. No second
ACME order exists to compete for the budget. Because the wildcard in
`kube-system` is already valid, this restores HTTPS without waiting for the
rate limit to lift.

**Files:** `core/platform/cilium.go`, `core/platform/cert_manager.go`

## Upgrade Gotchas

**`just core talos up` never upgrades a running node.** Images download to a
fixed filename, so the Proxmox file ID is unchanged and existing VM disks keep
their old Talos. Only newly created VMs get the new image.

**Upgraded nodes keep unparseable iSCSI node records, and reboots do not clear
them.** The post-upgrade open-iscsi rejects `node.session.conn_reopen_log_freq`,
which the older version wrote into
`/var/lib/iscsi/nodes/<iqn>/<ip>,3260,1/default`. `iscsiadm -m node -o show`
parses *every* record, so one bad file fails the whole call with exit 7 and all
Longhorn attachments on that node break: frontend startup fails, the engine
exits, Longhorn logs `DetachedUnexpectedly ... faulted`, and it retries every
~5s forever. The records live on persistent `/var`, so rebooting does not help.

worker3 and worker4 both had stale records; worker1 and worker2 did not.
`just talos-upgrade` now runs `just longhorn-repair-iscsi` after the health
check, so this repairs itself. The recipe reads the rejected parameter name out
of iscsiadm's own error rather than matching a hardcoded string, so it still
works when a later release renames a different one. Run it standalone at any
time — it is idempotent and silent when there is nothing to fix:

```bash
just longhorn-repair-iscsi
```

**A stale L2 announcement lease blackholes every LoadBalancer IP.** After the
Cilium agent rollout, the lease holder kept renewing every 15s and
`db/show l2-announce` still listed `192.168.1.220 ens18`, but the node had
stopped answering ARP. The Gateway reported `Programmed=True` and Envoy was
healthy on all nodes. The fingerprint: **in-cluster requests to the Gateway
return 200 while the LAN times out on both ports.** Force re-election:

```bash
kubectl delete lease -n kube-system \
  cilium-l2announce-kube-system-cilium-gateway-homelab-gateway
```

Ignore `Proxy Status: 0 redirects active` — with `Envoy: external` the Gateway
listeners live in the cilium-envoy DaemonSet and are never counted there.

**A node whose datapath does not recover cannot reboot gracefully.** worker1's
agent stayed `0/1` on the correct image while kubelet's KubePrism requests
(`127.0.0.1:7445`) returned EOF. `talosctl reboot` then hung at
`unmountPodMounts`: the node had a Longhorn RWX volume mounted over NFS from a
share-manager ClusterIP it could no longer reach, so the unmount blocked
forever — the reboot that would fix Cilium was blocked by Cilium being broken.
`cri` and `kubelet` read `Finished/Fail` while the Talos API stayed up, since
apid survives the shutdown sequence. Break it with:

```bash
talosctl --talosconfig ~/.talos/config reboot --nodes <ip> --mode powercycle
```

Pulumi marks the Cilium release failed in this situation
(`failed to become available within allocated timeout`) even though the
DaemonSet reached every node. Re-running `just core platform up` after the node
recovers is idempotent and finishes the remaining resources.

**Kubernetes does not ride along.** `just talos-upgrade-k8s <version>` is
separate. Cluster is on k8s v1.36.0; Talos 1.13.8 defaults to 1.36.2.
