## Bug Fixes

### Talos upgrades were impossible — `machine.install` was being deleted

**Root cause:** nodes boot `talos.platform=metal` despite nocloud factory
images, and the metal installer refuses to upgrade without `machine.install`.
`patchTalosConfig` in `core/platform/talos.go` had been deleting that section
since Feb 2026, so no node ever carried one. Every upgrade failed with
`install instructions are required in metal mode`.

**Fix:** `basePatch` declares `install.disk: /dev/sda` and the unconditional
delete is gone. sda is the 215 GB virtio system disk; sdb is Longhorn storage
and is never an install target.

**File:** `core/platform/talos.go`

---

### `--preserve` forced the deprecated upgrade path

Talos 1.13 upgrades via LifecycleService, which preserves data and drains the
node itself. Passing `--preserve` forced the old MachineService.Upgrade
fallback.

**File:** justfile (`talos-upgrade` recipe)

---

### Optional drain skip for nodes that cannot be evicted

Longhorn gives each instance-manager a PDB allowing zero disruptions while a
volume is attached, and a single-instance CNPG cluster's PDB can never release
its only pod. The drain burns its timeout, `talosctl` exits before rebooting,
and the node is left cordoned on the old version. `just talos-upgrade <ip>
[base|gpu] [drain]` now takes an explicit drain toggle.

**File:** justfile

---

### Longhorn — control-plane toleration deadlocked all volume attachment

**Root cause:** `longhornManager.tolerations` carried the control-plane taint,
so a manager pod ran on each control plane and registered it as a Longhorn
node. Every registered node must then have the engine image deployed, but
engine-image DaemonSets receive only the global `defaultSettings.taintToleration`
(empty here) and schedule on workers only. EngineImages stalled at
`Engine image is not fully deployed on all nodes: 4 of 7`, state `deploying`,
and **no volume in the cluster could attach**.

**Fix:** dropped the toleration. Control planes hold no Longhorn disks and run
no PVC-backed pods. `longhornDriver` and `longhornUI` tolerations are retained —
those are Deployments and do not register Longhorn nodes.

**File:** `workloads/storage/longhorn.go`

This fix was cherry-picked to `v0.1.6` as `e4aea57` and applied ahead of this
release because it was resolving a live outage.

## Upgrade Gotchas

**`just core talos up` never upgrades a running node.** Images download to a
fixed filename, so the Proxmox file ID is unchanged and existing VM disks keep
their old Talos. Only newly created VMs get the new image.

**Upgraded nodes keep unparseable iSCSI node records, and reboots do not clear
them.** The post-upgrade open-iscsi rejects `node.session.conn_reopen_log_freq`,
which the older version wrote into
`/var/lib/iscsi/nodes/<iqn>/<ip>,3260,1/default`. `iscsiadm -m node -o show`
parses *every* record, so one bad file fails the whole call with exit 7 and all
Longhorn attachments on that node break: frontend startup fails, the engine
exits, Longhorn logs `DetachedUnexpectedly ... faulted`, and it retries every
~5s forever. The records live on persistent `/var`, so rebooting does not help.

Check every upgraded node — worker3 and worker4 both had stale records,
worker1 and worker2 did not:

```bash
kubectl exec -n longhorn-system <instance-manager-pod> -- \
  grep -rl conn_reopen_log_freq /host/var/lib/iscsi/nodes/

kubectl exec -n longhorn-system <instance-manager-pod> -- bash -c \
  'grep -rl "conn_reopen_log_freq" /host/var/lib/iscsi/nodes/ | while read f; do sed -i "/conn_reopen_log_freq/d" "$f"; done'
```

**Kubernetes does not ride along.** `just talos-upgrade-k8s <version>` is
separate. Cluster is on k8s v1.36.0; Talos 1.13.8 defaults to 1.36.2.
