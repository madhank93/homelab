Cilium and Gateway API

Phase 2. Risk: high, the CNI restart interrupts pod networking and can blackhole LoadBalancer IPs. Pins: charts.cilium in config/versions.yaml; Gateway API CRDs vendored in core/platform/manifests/. Applied with just core platform up.

Rules

Section titled “Rules”
  • One minor at a time (1.18 → 1.19 → 1.20), each on the latest patch of its line. It is the only path Cilium tests, up and down.
  • Check the Kubernetes compatibility matrix against the pinned Kubernetes.
  • Read the version’s upgrade notes for removed Helm values. Render the old and new chart with the values from cilium.go and diff the cilium-config ConfigMap.
  • Gateway API CRDs go first, as their own apply: each Cilium minor needs a minimum Gateway API release, and the operator enables the controller only for CRDs present when it starts.
  • After each bump, check the CiliumLoadBalancerIPPool and CiliumL2AnnouncementPolicy specs in cilium.go for field renames.

Never add wt0 to devices

devices stays ens18 and eth0. wt0 is NOARP/POINTOPOINT and Cilium’s TC BPF silently drops its frames. See NetBird peer.

Gates

Section titled “Gates”

Run every gate from a laptop on the LAN before the first change and after every apply. Do not start the next step until all pass.

Gate 4 exists because the LB pool in config/config.yml spans worker IPs. From 1.19 the datapath drops traffic to an LB-IPAM address on any port no Service uses (cilium/cilium#44430); 1.19.5 spares only the node owning the IP, so a worker whose IP is also an LB IP loses Talos API and kubelet access from everywhere else. ConfigureCiliumIPPool now skips node IPs when it builds the pool, so gate 4 should always be empty.

1.18 → 1.20 runbook

Section titled “1.18 → 1.20 runbook”

Three applies, one commit each. For each: just core platform preview, then just core platform up, then every gate. Abort on any replace, above all on cilium-ip-pool, cilium-gateway, cilium-l2-policy, a Helm release, or a Gateway API CRD (a CRD replace deletes every route).

  1. Gateway API CRDs v1.6.3, Cilium stays on 1.18.12. The preview must show the CRDs updated, the BackendLBPolicy CRD deleted, the safe-upgrades admission policy created, and cilium-ip-pool as an in-place update to cilium.io/v2 — never a replace, which releases every LoadBalancer IP. The experimental bundle keeps TLSRoute v1alpha2, which the 1.18 and 1.19 operators need to start (cilium/cilium#45139).

  2. Cilium 1.19.10. Never below 1.19.5, which fixes #44430 and #46010. Watch gate 3 while the DaemonSet rolls: if a node’s Talos API stops answering, roll back before the agent reaches the rest. 1.19 is untested on Kubernetes 1.36, so move on as soon as the gates pass.

  3. Cilium 1.20.4. Same commands and gates. An empty l2announce lease list with LB IPs still assigned is #48799 (externalTrafficPolicy: Local Services lose their announcement); the Gateway uses Cluster and is unaffected.

Rollback

Section titled “Rollback”

Back one minor at a time

Reverse the way up: 1.20 → 1.19.10 → 1.18.12. Never jump two minors down.

Check out the previous commit (or revert the bump) and run just core platform up; Pulumi runs a helm upgrade to the older chart. If Pulumi is not an option, helm history cilium -n kube-system and helm rollback cilium <revision> -n kube-system, then re-run Pulumi from the matching commit so its state agrees.

Leave the Gateway API CRDs and the cilium.io/v2 pool in place: 1.18 and 1.19 run on both. The safe-upgrades.gateway.networking.k8s.io admission policy refuses rolling the CRDs below the 1.5 line.

If every LoadBalancer IP goes dark afterwards

Section titled “If every LoadBalancer IP goes dark afterwards”

An agent restart can leave the L2 lease holder renewing normally, still listing the IP in db/show l2-announce, while it has stopped answering ARP. The Gateway stays Programmed=True and Envoy stays ready. The fingerprint: in-cluster requests to the Gateway succeed while the LAN times out.

Ignore Proxy Status: 0 redirects active: with Envoy: external the Gateway listeners live in the cilium-envoy DaemonSet and are never counted there.

Pulumi reports the release failed (failed to become available within allocated timeout) if one agent never goes ready, even when the DaemonSet reached every node. Fix the node, then re-run just core platform up; it is idempotent. A node whose agent will not recover cannot reboot gracefully either — power-cycle it. If its Talos API is dead, reset the VM from Proxmox, then re-run the gates.
